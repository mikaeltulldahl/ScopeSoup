# Design

What Scope Soup is: a server program with a web GUI that runs a software project's work loop with coding agents, for one person or a small team. It keeps work moving on its own, shows everything in one place, and asks people only for what needs them. The decisions behind this design are in `docs/DECISIONS.md`.

## Parts

```
            +--------------------- one process ----------------------+
 browser <--| server (HTTP, SSE)                                      |
            |    ^                                                    |
            |    | events                                             |
            |  store (SQLite: tables + append-only events)            |
            |    ^                         ^                          |
            |    |                         |                          |
            |  sync (poll hosts)        orchestrator (tick loop)      |
            |    |                         |        |                 |
            +----|-------------------------|--------|-----------------+
                 v                         v        v
           host adapters             queue engine   agent runner
           (GitHub, ...)             (pure)         (claude -p children)
```

| Directory | Holds | May import |
|---|---|---|
| `src/model` | The host-neutral types | nothing |
| `src/ports` | The interfaces a host adapter implements | `model` |
| `src/core` | Pure rules: lanes, turns, estimates, readiness | `model` |
| `src/queue` | The batch engine: chain, batch size, flake rerun, bisect. Pure: `(state, input) -> (state, effects)` | `model` |
| `src/store` | SQLite behind an interface; tables plus the events table | `model` |
| `src/hosts/<name>` | One adapter per host | `model`, `ports` |
| `src/orchestrator` | The tick loop, the agent runner, the usage check | everything above |
| `src/server` | HTTP, SSE, the status endpoint | everything above |
| `web` | The board (Preact), built with Vite | only the server's HTTP API |

The rule that matters most: `model`, `core`, `queue` and `store` never import a host. A test checks it (`src/core/boundaries.test.ts`).

## Model

Defined in `src/model/types.ts`. The work item is the root; everything else hangs off it.

| Object | Is |
|---|---|
| Work item | A piece of work with a state, dependencies, an optional verification and a priority |
| Change | A proposed set of commits for one or more items, with revisions |
| Verdict | One judgement of one revision in one dimension (review, risk, check) |
| Run | One execution of a check on one commit (a host's CI run, or Scope Soup's own) |
| Batch | Changes tested together, with the probes of a bisect |
| Session | One agent run on an item or a change, live or finished |
| Turn | Who must act next on an item, and why |
| Budget | The usage windows, what is used and what is reserved |

## Hosts

Ports are split by capability (`src/ports/host.ts`), so a deployment can combine hosts (one for work items, one for changes, one for CI), and a host that lacks a capability does not implement that port.

- Events from a host are hints. The core always refetches. A poll, a webhook and an SSH stream are then interchangeable, and a missed event costs only delay.
- Polling uses conditional requests (decision 9).
- A host adapter holds no project-specific conventions; a project's own conventions would be a layer on top of it. Scope Soup's own conventions on GitHub (comment markers, `Q1:`/`A1:` replies, labels) are such a layer, `src/hosts/github/conventions.ts`; the design is [`docs/github-mapping.md`](github-mapping.md).

### Hosts and players: the switches

What Scope Soup does when a project changes its host (Settings' Connect, decision 98, and Move back, decision 99) or a machine switches between singleplayer and multiplayer (Settings' Players, decisions 93 and 98).

| Situation | What happens |
|---|---|
| 1. Singleplayer on the meta branch, Connect to Jira or GitHub | The dialog checks the token and the host, lists the open Items to tick, moves the ticked ones (new issues first, then references, history and last the old Items' close) and then writes the shared `host`; the rest stay on the meta branch. |
| 2. Multiplayer on the meta branch, Connect | The same, and each other machine keeps its own per-host parts; at its next start it reads the new host, or, lacking the token or Jira email, shows "Set up this machine for <host>" and starts no agent. |
| 3. Multiplayer while a machine is busy | Connect (and Join theirs) is refused while a session runs here or an agent holds an unexpired claim on an Item, the only way other machines are seen, naming the busy machines. |
| 4. Singleplayer with Jira, switch to multiplayer, the remote has no meta ref | The switch needs no question, and the meta writer pushes this clone's meta ref (the shared settings) to the remote. |
| 5. Singleplayer, switch to multiplayer, the remote's settings name another host or project | The page shows both and asks: "Join theirs" keeps this clone's meta ref (its unshared Items leave the board) only in `refs/scopesoup-backup/meta-<commit>` and uses the remote's; "Make mine the project's" warns that it changes every machine and puts this clone's commits on top of the remote's. |
| 6. Singleplayer on the meta branch, switch to multiplayer, the same host and project on the remote | The switch needs no question, and the meta writer puts this clone's own commits on top of the remote's: Items merge and an id taken on both sides is renumbered. |
| 7. A new machine joins, or a project starts on Jira | Onboarding writes its private file (a new project that picks Jira in onboarding gets the Jira host in its first shared settings, checked as Connect checks it, decision 101); when it lacks what the project's GitHub or Jira host needs, its board shows the same "Set up this machine" dialog with the host filled in from the shared settings. |
| 8. Multiplayer to singleplayer and back | Switching off shares nothing more; switching on runs scenario 5's check again, and asks only if the remote's settings now name another host or project. |
| 9. Jira to GitHub, or either back | Two steps through the meta branch: "Move back to the meta branch", then Connect; Connect itself refuses to go from one to the other directly. |
| 10. GitHub or Jira, Move back to the meta branch | The dialog asks this machine's meta part (name, email, id prefix), lists the host's open issues to tick and whether they are closed or left open there; the ticked ones become Items in one meta commit (references between them rewritten, their comments as one log line, found again by `importedFrom` on a retry), then each old issue gets a comment naming its Item and is closed or left open; only then the shared `host` becomes the meta branch. Other machines without a meta part show "Set up this machine for the meta branch". |

## Items on a meta branch

For a project whose items live in its own repository (decisions 23 and 24), the host is `src/hosts/metaBranch`. It reads one ref, `refs/scopesoup/meta` (a fixed name; the project's shared settings are on it too, so finding them needs no setting), straight from the repository's object store with `git rev-parse`, `git ls-tree` and one `git cat-file --batch`. It never checks the branch out. It fetches and writes Items only when writes are switched on ("Writing to the meta branch" below); the shared settings fetch the ref and write it on every host (below). A repository without the ref is an empty project. It implements the work and change ports, and the ordinary sync fills the store from it. The cursor of a listing is the meta commit plus the ids it returned, so a listing on an unchanged ref is free and one after a move says which items went.

```
format                  the meta branch's format: a whole number and a line end
settings/settings.json  the project's shared settings: one JSON object
settings/log.jsonl      one line per save of the settings: who changed what
requests/<yyyy-mm>.jsonl  a month's picks asked of the machine that runs an Item's work, and its answers (decision 104)
items/<id>/item.md      what the item is
items/<id>/log.jsonl    what has happened to it
```

Anything else under `items/` (a name that is not an id, another file) is skipped and named in the adapter's read report. So is an `item.md` or `log.jsonl` whose mode is not a regular file (`100644` or `100755`): a symlink or a submodule entry is never followed or read. The item reader reads nothing outside `items/` but `format`.

**The shared settings** (`src/hosts/metaBranch/settings.ts`, `src/config/metaSettings.ts`). Every project has the meta ref, on every host: a meta branch project keeps its Items next to the settings, a GitHub-host project has the ref for the settings alone (as it has `refs/scopesoup/merge-queue`). `settings/settings.json` holds the keys of `docs/RUNNING.md`, "The project's configuration" (the private file holds the rest; a key in the wrong place is refused). `settings/log.jsonl` is append-only like an item's log; its lines have the kind `settings` and `changes`, a list of `{ key, from?, to? }` (the dotted path of each changed value, absent `from` or `to` meaning there was none). A save is one commit by the writer ("Writing to the meta branch"), with the person who saved as the commit's author and as the line's `by`, and the two files as the only changed paths. Scope Soup reads the settings from the local ref with `git cat-file` (again only when the ref moved) and shares the ref with the private file's `remote` at start and every minute, with or without Item writes. Adding these files is not a breaking change: the format stays 1, and an older reader skips them.

**The format** (decision 63, `src/hosts/metaBranch/format.ts`). `format` is a regular file holding a whole number (no leading zero) and an optional `\n` or `\r\n`; a branch without it is format 0, everything Scope Soup wrote before the format entry. It is raised only for a breaking change; a new log kind or an optional field is not one (older readers keep and ignore them). This Scope Soup is format 1: format 0 plus the file. The read report has `format` (`{ format, note }`) only when the branch is not at this Scope Soup's format (`format` null when the file cannot be read). A newer format, or a file that cannot be read, is read only: the items are read as usual, and the writer refuses every write ("this project's data is from a newer Scope Soup; upgrade") and puts none of this machine's unshared commits on top of it (they stay on the local ref). An older format is written to as it is when every step from it only adds (`oldFormWritable`; true for 0 to 1); otherwise writes wait for the migration. The migration (`Writer.migrate`, driven by `src/hosts/metaBranch/migrate.ts`) is one commit: the steps from the branch's format to the current one, one per format, then the new `format`, on top of the remote's tip (fetched first), with the machine's trailer, and pushed. Only the machine that holds the merge queue lease makes it (decision 31; `refs/scopesoup/merge-queue`, taken for the migration alone at any level and let go after; none is needed without a remote or with `SCOPESOUP_MERGE_QUEUE=off`). The migration does not run while this machine holds the lease for a merge. A new branch's first commit carries `format`; such a root commit put on top of an existing history (a machine that wrote before it ever fetched) leaves `format` out, so only the migration changes a shared branch's format. Two migration commits that raced (only possible without the lease) make the same change, and the second is dropped when it is put on top. Items are listed in plain code-unit order of their ids. A file over 1 MB (`MAX_FILE_BYTES` in `git.ts`) is not read, from sizes taken from the tree before any blob is read: an `item.md` over it makes its item malformed, a `log.jsonl` over it counts as one malformed line and the log as empty. Other items are not affected. The text of a problem echoed into `hostState` is cut at 200 characters.

The repository directory (`SCOPESOUP_META_REPO`) must be a repository's own top level (or a bare repository, or a `.git` directory); a plain subdirectory of another repository is refused with a message, because git would otherwise read the outer repository. A submodule's directory is a top level and is accepted. git is spawned without `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR` and `GIT_NAMESPACE`, and a git process that runs over 60 seconds is ended. When Windows refuses to create a process (EPERM or EACCES and no pid, so nothing ran), the start is tried again up to five times over about 750 ms, logged once; a process that started is not run again for that (`src/hosts/spawnRetry.ts`, also used by the orchestrator and the tests). A git that started is run once more only when it exits with 4294967295 (ended from outside, not by git) with nothing on stderr, and only for a command that is safe to repeat: a read, a write of an object by its content (`hash-object`, `mktree`, `commit-tree`), a read of one config value, or an `update-ref` that names the old value; each retry is logged, and the test reporter lists them (`src/hosts/gitRetry.ts`). A ref that points at something that is not a commit (a tree, a blob) is an error; only a missing ref is an empty project.

**Ids.** The directory name is the id, and the only place it comes from. An id is a letter or digit followed by up to 63 letters, digits, `-` or `_` (`A-12`). So an id has no `.`, no path separator and no leading `-`: it cannot leave `items/<id>/` or be read by git as an option. The same rule applies to `parent` and `blockedBy`. The meta ref must be `refs/` followed by segments of letters, digits, `.`, `_`, `-`; branch names in log lines follow the same rule under `refs/heads/`. Commit ids git prints are 7 to 64 lower-case hex digits; a `sha` in a log line must be a full id: exactly 40 or 64 lower-case hex digits.

**`item.md`** is a header between two lines that are exactly `---`, then the description in markdown.

```
---
id: A-12
title: Add a regression suite
state: doing
labels: tests, core
parent: A-3
blockedBy: A-10, A-11
verification: pnpm check runs the new suite
priority: major
---

The description.
```

What the header accepts, and nothing more (it is not YAML):

- An optional UTF-8 byte order mark; `\n` or `\r\n` line ends.
- Each line is `key: value`. A key is a letter followed by letters and digits. The value is the rest of the line after the first `:`, trimmed, taken literally: no quoting, no escapes, no values over several lines. Blank lines and lines starting with `#` are ignored.
- `title` and `state` are required. `state` is one of `todo`, `doing`, `waiting`, `done`, `abandoned`.
- `labels` and `blockedBy` are lists: comma-separated, each entry trimmed, empty entries dropped; one pair of enclosing `[` `]` is allowed.
- `id` is optional and, when present, must equal the directory name. `parent` is an id. `duplicateOf` is an id: an `abandoned` item closed as that one's duplicate (ignored on any other state, and dropped by an edit that reopens it). `verification` is one line. `priority` is `blocker`, `critical`, `major` or `minor` (none counts as `major`; `src/model/priority.ts`).
- An empty `parent:`, `risk:` or `priority:` is accepted and means none. The closing `---` must be exactly three dashes with nothing after them (no trailing spaces); the opening one the same.
- Other keys are kept in file order (a writer puts them back) and otherwise ignored.
- Any other line, a key given twice, or a value that does not fit its field makes the item malformed. A malformed item is still listed, with state `waiting`, the title `<id>: item.md cannot be read` and `hostState` `malformed: <the problems>`, so a person sees it and agents leave it alone. It never breaks the read of other items. An item with a log but no `item.md` is malformed the same way.

**`log.jsonl`** is append-only: one JSON object per line, never edited or removed. Every line has:

| Field | Is |
|---|---|
| `at` | ISO 8601 time with a zone. Writers write UTC with `Z`: `2026-11-18T09:00:00Z`. A reader also accepts an offset (`+02:00`). |
| `by` | `{ "who": "robin", "machine": "laptop-a", "agent": false }`. `machine` and `agent` are optional. Writers write the object form; a reader also accepts a bare string, read as `who` (no machine, not an agent), the same actor as `{ "who": ... }`. |
| `kind` | A short lower-case word: a letter, then up to 39 of `a-z`, digits, `-`, `_` |

The kinds and their own fields (all optional unless named):

| `kind` | Fields | Folded into |
|---|---|---|
| `created` | | Nothing (the item page's log) |
| `edited` | `changed` (list of the fields changed) | Nothing (the item page's log) |
| `claimed` | `until` (time, required) | The holder |
| `released` | `reason`; `of` (the holder, `who@machine`, when someone else releases a person's hold) | The holder, or any person naming the holder in `of` |
| `session` | `role`, `model`, `outcome`, `summary`, `durationMs`; Scope Soup adds `next` (the step that comes next) and `size`; later `sessionId` (Scope Soup's session, which links the step to its cost, stream and chat), `costUsd` (when known), and for a triage `ready` (its `summary` is then the verdict in words). Older lines may carry `risk` and `riskReason`, which nothing reads | Nothing (the item page's log and Rounds table) |
| `question` | `question` (required), `options` (list; each `{ label, description }`, or plain text from older lines), `recommendation` (the label of the recommended option), `context` (a note beyond the options); Scope Soup adds `parked` (why the item is parked), `retry` and, for a triage's rewrite, `rewrite` (the round); a proposed restructuring adds `proposal` with `original` (`keeps`, `umbrella` or `replaced`), `parts` (each `{ title, description, verification, goes, into? }`), `carried` (the answers carried over) and `reason`. An older line whose `proposal` has `description` and/or `verification` instead of `parts` (a proposed rewrite, removed) is kept in the log and the history but is not an open question | The open questions (a `proposal` is kept on the question) |
| `answer` | `answer` (required), `to` (the `at` of the question answered), `toBy` (that question's `by`; optional) | The open questions |
| `assumption` | `decisions` (list; each `question`, `chosen`, `others`, `why`), the decisions an implementor took itself as cheap to change later; also `assumption` in words, for older versions. An older line with only `assumption` is kept and shown in the history, and is no decision | The Item's decisions (`assumptions`), open until a verdict names them |
| `accepted` / `overturned` | `to` (the `at` of the `assumption` line), `n` (the decision's place in it, from 0); `overturned` adds `answer` (a person's decision) and either `item` (the new Item that reworks it) or `work: true` (the change had not merged, so the answer went into the running work and no Item was made) | Settles that decision; the first verdict counts |
| `revision` | `sha` (required, full), `branch` | The change |
| `review` | `sha` (required, full), `verdict` (`pass` or `fail`, required), `findings` (text or list) | The change's review verdicts |
| `check` | `sha` (required, full), `verdict` (required), `command`, `findings`; later `batch` | The change's `ci` verdicts |
| `merged` | `sha` (required, full), `target` | The change's state |

**The fold.** The order of the lines in the file does not matter, so two laptops' logs can be merged by keeping both sets of lines. Rules 1 and 2 shape the input of every other rule.

1. Order. Lines are folded ordered by `at` as an instant (an offset is converted, so `10:00+01:00` is `09:00Z`), then by `by` in its canonical text form (the JSON of `[who, machine or null, agent]`, compared by code units), then by the line's position in the file. The sort is stable.
2. Duplicates. A line's identity is its whole parsed content: the same `at` instant, `by`, `kind` and fields (times and writers compared in canonical form, so a bare `by` equals the object form). Identical lines are dropped before folding, the first kept. Revisions with the same `sha` are one revision: the first stays, and a later line for the same sha, by whoever, changes nothing. So the same `question` twice plus one `answer` leaves no open question.
3. `merged` counts only for the newest revision (the last in fold order). A `merged` whose `sha` is another revision's is read and ignored; a revision after it opens the change again. A `sha` that is not a full id (40 or 64 lower-case hex digits) makes its line malformed.
4. Verdicts. A change has the latest `review` per reviewer and the latest `check` per command. If a reviewer or command has a verdict on the newest revision, the latest of those is taken, even when a verdict on an older revision was written later. Otherwise the latest on an older revision is taken and marked stale.
5. Done. When the newest revision has merged, the item is done whatever `item.md`'s `state` says (the log is mechanical and append-only; the header is edited by hand). The work item maps to state `done` (its `hostState` still shows the header's `state`), it is no open child of its parent, and the change is merged. The exception is an item whose `item.md` cannot be read: it stays `waiting`, so that a person sees it. On GitHub, an item whose change has merged shows Done on the board while its issue is still open (the `mergedWork` rule in `src/core/lanes.ts`) and is never started again; merging closes the issue when the host is writable, and with `write: false` the board says to close it by hand.
6. Times and actors. Writers write `at` and `until` in UTC with `Z` and `by` as the object form. Readers accept an offset and a bare string, and map every time to UTC ISO 8601 with milliseconds (`2026-11-18T09:00:00.000Z`) and one actor for both spellings of the same `who`.
7. Holder. `claimed` requires `until`; a `claimed` without a valid `until` is malformed (kept and counted), so a dead laptop cannot hold an item forever. A `claimed` takes the item when nobody holds it, when the holder claims again (renewal), or when an agent holder's `until` has passed by the line's `at`; otherwise the earlier claim stands. A person's claim (`agent` false) never runs out, whatever its `until` says: people have no stall timer, so only a `released` line ends it. The holder's own line is, for an agent, one with the same `who` and `machine`; for a person (a person is not tied to a machine), one with the same `who` from any machine, so a person renews, hands back or releases their hold from any board. `released` lets go when it is the holder's own, or (people are equals) when a person writes it with `of` naming a person holder as `who@machine` (`who` without a machine). An agent's claim is let go only by that agent.
8. Questions. A `question` is open until an `answer` closes it. An answer's `to` is the `at` of the question (as an instant). It closes every open question with that `at`, unless it carries `toBy`, the question's `by` (a name or an object, compared on `who` and `machine`); then it closes only those by that writer. An answer without `to` closes the newest open question. An answer whose `to` or `toBy` is not valid is malformed. An open question sets the item's `needsDecision`.

Besides: there is a change when there is a `revision` line. It has the item's id (it has no number of its own), the branch of the newest revision that names one, and every revision oldest first. An abandoned item's unmerged change is closed. The target is the `merged` line's, else the host's setting (default `main`). Once the change is on main Scope Soup writes `state: done` to the header (decision 114), whether the queue merged it, the session did, or a person merged the handed-over branch. `session` lines are kept and not read; `assumption`, `accepted` and `overturned` lines give the Item's decisions. The item's `updatedAt` is the newest `at` in its log, else the meta commit's time.

The read gives each item its log twice: `history` (each line in words, for the item page) and `log` (each line with its fields). Open questions are `openQuestions`, each with its `at`, `by`, `context`, options (`{ label, description }`; plain text from older lines is read as a label) and recommendation; an answer names one by those.

A line that is not JSON, not an object, or lacks a valid `at`, `by` or `kind` is kept with its problem and counted; so is a known kind whose fields do not fit (a `review` without `sha`). A kind Scope Soup does not know is kept and counted. Neither is ever fatal. Text from items and logs is data: it is never executed, and nothing from it reaches a path or a git argument without the checks above.

**A conflict.** `items/<id>/item.conflict-<12 hex>.md` (a regular file) is a version of `item.md` put aside because `item.md` was changed on two machines at once; the hex is the start of that version's blob id. The reader does not read it, but an item with one is everyone's turn: it gets `needsDecision`, its `hostState` says `<state>; conflict: item.md was changed on two machines, the other version is in <files>`, and the read report lists it under `conflicts`. Its `item.md` is read as usual. Agents leave it alone, as any item that needs a decision.

## Writing to the meta branch

With writes switched on (`allowWrites`; `SCOPESOUP_META_WRITE=1`), `src/hosts/metaBranch/writer.ts` creates items, edits `item.md` and appends log lines, through the write port (`createWork`, `editWork`, `appendLog`). Each returns what became of the write: the item (whose id may have moved, see below), whether it is shared, pending (with why) or local only, and whether the item is in conflict. Without writes the host changes nothing in the repository, not even by a fetch; the shared settings still fetch and push the ref with the same writer, for their own files.

**One write, one commit.** A write starts from the tip and tree this writer remembers from its last write, so it does not read the ref and the tree again (a write is at most 5 git processes, with sharing counted apart). A refusal or a no-op found on the remembered state is checked again against a fresh read before it counts, and the remembered state is dropped when the ref has moved. It builds the new files, writes them with `git hash-object`, the changed directories with one `git mktree --batch` (their ids computed first and checked against git's), the commit with `git commit-tree`, and moves the ref with `git update-ref <ref> <new> <old>`, the value it read. No checkout, no working directory, no index. When another writer on the machine moved the ref first, the write is done again from the new value: freshly read, re-planned, checked again. The ref is never moved while a working copy of the repository has it checked out.

- Every changed path must be `items/<id>/item.md`, `log.jsonl` or a conflict file of the item written, with an id checked as above; titles and other text only ever go into files. A save of the settings changes only `settings/settings.json` and `settings/log.jsonl`; a pick's request or answer only that month's `requests/<yyyy-mm>.jsonl`. The other exception is `format` in the first commit of a new meta branch, and the migration's commit ("The format" above).
- Before planning, the write checks the format of the tree it starts from (the `format` blob read once per blob id): a newer or unreadable one refuses the write.
- `item.md` is written by `serializeItem` so that the reader, reading the file's bytes, gives back exactly the same fields, or the value is refused (a line break, U+2028 or another control character, a lone surrogate, white space the reader would trim, a comma or bracket in a label, a key twice, a file over 1 MB). The board puts what a person typed in that form first (`canonicalItem`: trimmed, `\n` line ends, no blank lines around the description).
- An edit by Scope Soup writes the whole header again in this canonical form: known keys in a fixed order, unknown keys kept in their order, `\n` line ends. Comment lines (`#`) and blank lines in a hand-written header are not kept.
- A log line is written by `serializeLogLine`: `at` and times in `until` and `to` in UTC with `Z`, `by` as `{ who, machine, agent }` with this machine's name, a `kind` that is a short lower-case word, fields that are plain JSON. It must read back as one entry with no problem, a known kind with its required fields; else it is refused. A line is at most 16 KB (`MAX_LINE_BYTES`): a caller shortens a long summary. A line identical to one the log has is not written again.
- **Append-only.** A write that changes a log checks that every old line is still there, unchanged, in its place, with lines only added at the end. A line is never edited or removed.
- **Sizes** (`limits.ts`): the reader leaves a file over 1 MB unread. One append may not take a log past 768 KB, so the lines other machines add before the next fetch still fit when logs are merged. A merge is never refused for size: refusing it would stop the sharing of every other item; a merged log past 1 MB spoils only its own item's log.
- **New ids:** the machine's prefix (`SCOPESOUP_META_PREFIX`: one per machine, never shared; Scope Soup warns at start when it is not set) and one more than the highest number with that prefix among the items on the ref the write read, as a counter of any length. The id must be free on that ref. Two writers on one machine both read the same number; the second one's `update-ref` fails, and its write, done again, takes the next number. Two machines that were given the same prefix by mistake can both create the same id before they share: see "Putting own commits on top".
- Commits are made as the configured person (`SCOPESOUP_META_AUTHOR_NAME`, `..._EMAIL`), passed to git directly, never from the machine's git config. The local plumbing runs with hooks, signing and automatic gc off; a push is not signed (`push.gpgSign=false`) but runs the repository's hooks. Inherited `GIT_*` variables that name a repository or an identity are removed, `git replace` is off (`GIT_NO_REPLACE_OBJECTS`), and nothing may prompt: `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, and ssh in batch mode (the user's own `GIT_SSH_COMMAND` or `core.sshCommand` with `-o BatchMode=yes` added, or `-batch` when that command is PuTTY's `plink` or `TortoisePlink`; plain `ssh -o BatchMode=yes` otherwise; left alone when `GIT_SSH` names another program). Writing needs git 2.29 or newer, checked once.
- **Time limits.** Every git process has one (fetch, push and ls-remote five minutes, the rest one). When it passes, git and everything it started (a hook, ssh) are ended and the pipes closed, and the call fails at once; a git that exited while a leftover child holds its output settles two seconds later, and its time limit no longer applies (its pid may be reused). So a hook or an ssh that never ends cannot hold up writes or reads. Elsewhere than Windows git runs as its own process group, and the group is killed. On Windows Scope Soup ends the tree the way every Windows tree kill does (`src/hosts/processTree.ts`): one PowerShell process lists the processes (`Get-CimInstance Win32_Process`: pid, parent pid, creation time; under a second here, twenty seconds at most) and walks down from git, taking a child only when it was created no earlier than its parent, because Windows reuses pids and a process created before its supposed parent is an unrelated one. Git itself must be the process that was started (its creation time inside the moment of the spawn), or nothing is ended. Git for Windows runs hooks in MSYS `sh`, whose children hang off no living Windows parent, so Scope Soup also lists the MSYS processes with Git for Windows' own `ps` and adds every one started under that tree and created after git. Each process is then ended by its own pid, never with `taskkill /T`, after its creation time is checked once more. A process that left that tree by itself (started with `setsid`, or a service it asked for) is not reached; and when either listing fails, the error says that a hook or ssh may not have ended and processes may be left. `stop()` on the host ends every git still running the same way: Scope Soup calls it on shutdown, so a push in flight does not outlive it.
- **Lock files.** A git ended in the middle of a ref update can leave `<ref>.lock` behind. At each sharing round a lock older than ten minutes is removed for Scope Soup's own scratch refs (`refs/scopesoup-remote/...`, `refs/scopesoup-incoming/...`). One on the meta ref, or `packed-refs.lock`, is only reported (`lastSharing()`, with the path): it is the repository's, and a person deletes it when no git is running.

**Sharing.** With a remote (`SCOPESOUP_META_REMOTE`, default `origin`; a repository without it, or `none`, is local only and writes still work):

- After each write the ref is pushed, `<commit>:<ref>`, fast-forward only: never `+`, never a force. The push runs the repository's own hooks (a `pre-push` hook may be slow).
- What was last fetched is kept under `refs/scopesoup-remote/<remote>/<ref without refs/>`, Scope Soup's own ref (not `refs/remotes/`, which maps branches only), so a hidden ref such as `refs/scopesoup/meta` works like a branch. The remote is asked with `git ls-remote <remote> <full ref>`; a fetch uses the explicit refspec `+<ref>:refs/scopesoup-incoming/<remote>/<...>`, and what it brings is checked before it is taken.
- A refused push is told apart from other failures by asking the remote: if its ref moved, someone was first, so fetch, put the own commits on top, push again, at most five pushes per round (`pushAttempts`). Then the commits stay on the local ref and go with the next round. Any other failure (a hook, rights, the network, a time limit) is reported, not retried.
- Before reading, the ref is fetched, at most once a minute (`SCOPESOUP_META_FETCH_SECONDS`). A problem with sharing never fails a read; it is in the writer's sharing report.

**Putting own commits on top.** A pushed commit is never rewritten. Scope Soup knows exactly which commits are this machine's own and unshared, and only those are ever put on top again, moved to another id or required to survive:

- Every commit the writer makes ends with the trailer `ScopeSoup-Machine: <machine>`.
- `refs/scopesoup-local/shared/<remote>/<ref without refs/>`, Scope Soup's own, is the last commit of the local meta ref known to be on the remote: set after a push that went through, and after the local ref is brought up to a fetched one.
- This machine's own unshared commits are the first-parent line from that commit to the local tip, and each must carry this machine's trailer. A commit there without it was not made here: nothing is put on top, and sharing stops with a message.
- With that commit present, the fetched tip must contain it; if not (the remote was rewritten, or it is another remote), nothing is taken and the fetched commit is set aside under `refs/scopesoup-incoming/...`.
- With it absent and no local meta ref, the fetched history is taken as it is. With it absent and a local history (the first share from this machine), that history is put on top only if every one of its commits carries this machine's trailer; otherwise the two histories are unrelated and Scope Soup refuses rather than guess.

Each own commit, oldest first, is made again on top of the fetched one as a three-way merge of its change (its parent, itself, the new tip), keeping its author and message:

- A path only this side changed takes this side's version; one only the other side changed keeps theirs.
- `log.jsonl` (an item's, the settings' `settings/log.jsonl`, or a month's `requests/<yyyy-mm>.jsonl`) changed on both sides: both sets of lines. The other side's log stays as it is (it may be pushed), and this side's new lines that it does not have follow, in the order they were written. The file's order does not matter to the fold, which orders by `at`, then `by`.
- `item.md` changed on both sides, differently: a real conflict. The other side's version stays in `item.md`, this side's goes to `item.conflict-<blob>.md` beside it. Neither is lost, and the item is everyone's turn. A third machine's version goes beside it too.
- **Resolving.** While the item is in conflict an edit is refused, unless it names the versions it settles: `editWork(..., { resolveConflict: { supersedes: [blob ids] } })`, the ids as `versions(id)` gives them to the person. That edit writes `item.md` and removes only those versions. A version the person did not see (one that arrived after they looked) stays, the item stays in conflict, and the outcome says so. Log lines and every other item are written as usual meanwhile.
- `settings/settings.json` changed on both sides: the values this side's save changed are made again on the other side's settings, so two saves of different keys both merge, and a value both changed takes this side's (the save put on top is the later one, as a compare-and-swap that lost is made again on the newest settings). The result is not validated here; Scope Soup's loader refuses settings that do not validate and keeps the last good ones.
- A conflict file one side removed (a resolution) is removed. Any other file changed on both sides is not Scope Soup's to merge: nothing is pushed, and the problem is reported.
- **An id taken on both sides.** If an item whose create is among this machine's own unshared commits has an id the other side has meanwhile used for another item (two machines with one prefix), the item is created again under the next free id with that prefix: its files move, and in the `item.md` of this machine's own new items the `id:`, `parent:` and `blockedBy:` lines follow the move (nothing else in them changes). Log lines move with the item byte for byte, even when their text names the old id (a branch name such as `scopesoup/Q-1`). Only such an item can move: an item that existed when this machine last shared never does, and the code refuses it. Two different items are never merged into one. The sharing report and the write's outcome (`movedFrom`) name the new id, and the move is recorded in `<git dir>/scopesoup/moved-ids.json`. For an hour after the move a write from this machine to the old id is refused with the new id named: whoever asks may still hold the old id from an earlier outcome, and the old id is now the other machine's item. (Redirecting it instead would write into the wrong item whenever the caller meant the other machine's.)
- A commit of this side that removed or changed a log line is refused, and so is a result that would lose any line this machine's own unshared commits wrote (lines compared as a set: identical lines are one line, as the fold counts them).

**A history that lost something.** A fetched ref must contain the commit last fetched, be linear since then (first parents, no merge commit), and no commit along it may remove or change a log line its parent had: each step is checked, not only the two ends. If not, it is not taken: the local ref and `refs/scopesoup-remote/...` stay as they were, nothing is pushed, the fetched commit stays at `refs/scopesoup-incoming/...` for a person to look at (`docs/RUNNING.md` says how), and the sharing report says so. Writing and reading go on locally. A machine that has fetched nothing yet takes any history as the remote's: it saw nothing there that could be lost, and what it puts on top is only its own unshared commits, by the rules above. Checking the whole history once instead would refuse a remote for something that happened before this machine joined, which only a person can judge.

**Accepting a refused history** is one operation, `Writer.accept()`, run by a person as `pnpm meta:accept`: it saves the local meta ref under `refs/scopesoup-backup/<time>`, makes the fetched commit the local, the fetched and the shared state, puts this machine's own unshared commits on top of it by the rules above (and reports those it cannot), and pushes. Lines the accepted history removed stay removed: nothing older than this machine's own unshared commits is put back.

**Fixed for good once machines hold real history.** Lines are compared byte for byte, so the writer's key order (`at`, `by`, `kind`, then the fields), its time format (UTC, `Z`, whole seconds unless there are milliseconds) and `by` as `{ who, machine, agent }` must not change; nor may the conflict file's name (`item.conflict-<first 12 hex of the blob id>.md`). The history is linear on first parents. An item is never deleted or renamed by a write (only by the id rule above, before it is shared).

## Store

One SQLite file (`src/store`).

- Plain tables are the source of truth.
- One append-only `events` table is written in the same transaction as each state change. Its sequence number is the SSE event id, so a browser resumes from `Last-Event-ID`. Events are never read to compute state.
- Raw agent streams go to files, one per session; the store holds only an index row.
- One writer: the process itself.
- A schema version in `PRAGMA user_version` (decision 64, `src/store/schema.ts`): `openStore` migrates an older database in one transaction, one step per version, keeping a copy `scopesoup.v<old>.sqlite` before a step that changes the schema; a newer one is opened read only and every write is refused.

## Orchestrator

A tick loop, in this order (after Symphony's specification):

1. Reconcile: check running sessions for stalls, refresh host state.
2. Load and validate the project's configuration; a bad reload keeps the last good one. It is in two places, each key in exactly one (`src/config/shared.ts`): this machine's private `scopesoup.config.json` (its name, where the repository is, local paths, what it may spend) and the project's shared settings, `settings/settings.json` on the meta ref `refs/scopesoup/meta` in `repoPath`, read with `git cat-file` (again only when the ref moved, and at most every 2 seconds) and fetched from `remote` at start and every minute. Validation (`validate.ts`) runs on the two taken together; placement is checked first. A project setting saved on the Settings page is one meta commit (`src/config/metaSettings.ts`), in effect at once.
3. Ask the usage check whether work may start.
4. Pick ready items; dispatch into free slots, as the level allows and only while agents are started.

Judgement points call the agent CLI (`claude -p` today, through its provider) with a prompt template, a JSON schema for the answer, a tool allow-list and a turn limit. The program reads the structured result. The judgement points are: the triage at an item (the `triage` role, which for an item too large for one change also proposes its parts), implement, and review.

**The prompts** are minimal: `prompts/triage.md`, `implement.md` and `review.md`, under 50 lines together. Each is the Item between markers (data, not instructions), where the session works, the project's own CLAUDE.md to follow, what earlier sessions on the Item did and what a person answered (`{{history}}`, empty on a first or resumed session; decision 112), for the implementor the titles and descriptions of the Items linked to its Item (`{{linked}}`: the triage's `conflictsWith`, `related`, `blockedBy` and `blocks` links and the host's blockers, up to 8, each description clipped to 1200 characters, marked as data; empty when there are none; decision 115), the commands it may run (`{{allowedCommands}}`, built from `roles.<role>.allowedTools`, with one line of shell facts: one command per call, no chaining, no heredocs, commit with `-F`), and the answer it gives. Each has a small schema: the triage answers `ready`, `notReadyReason`, `size`, `questions` (options and a recommendation each), `rewrite` (the rewrite: the description as if every recommendation is taken), `links` (typed links to other Items, found with `item list --search` and `item show`), `labels` (adds and removes of the repository's existing labels, never `scopesoup:*`; `{{labels}}` lists them), `blockers`, `paths`, `restructure` (only when the Item should be split, folded into another or is a duplicate), `drafts` (separate work found, for a person's Approve) and `aboutOthers` (the rewrite and its questions are parked for a person until accepted, edited or rejected; another answer runs the triage again; only `blockedBy` acts by itself, see docs/RUNNING.md); implement answers `done`, `summary`, `mergedAs` (the commit on main or the pull request's URL) and a `question` when it stopped for one; review answers `verdict` and `findings`. A command the permission check refused is read from the session's result (`permission_denials`), not asked for. The implement prompt's end (`{{finish}}`) depends on the level: at level 2, and at level 3 after the reviewer approved, the session merges to main and pushes the way CLAUDE.md says (or opens a pull request); otherwise it commits on its branch and stops. Scope Soup marks the Item done when the remote's main contains the branch head (fetched and checked after the session, `merged` written as at merging), or contains the squash commit `mergedAs` names (new since the work started, with the branch's files as the head has them), hands it over when `mergedAs` is a pull request's URL, and parks it for a person otherwise (docs/RUNNING.md, "Merging by the session"). At level 3 an approval resumes the implementor with "Approved. Merge now as CLAUDE.md says." The prompt's `{{finish}}` is fixed when the session starts, so a level change applies to work that starts after it: when the answer of a session that was told to merge arrives at a level where it would only commit (the level was raised), and `mergedAs` is shown by the remote's main (head contained, or the squash commit), the Item is finished as after a level 2 merge, with an event naming the level it started at, instead of escalating an "empty branch"; a session told not to merge that merged anyway is escalated with that said (decision 108).

**No fix role.** Review findings and a failed merging (check, conflict, red batch) go back to the implementor: the job keeps the implementor's agent session id (`agentSession`) and the message (`resumeWith`), and the implement step resumes that session (`claude --resume <id>`) with only that message ("The reviewer asked for these changes: ... Fix them and commit. Answer as before."). Without a known id, or after a resumed session failed, a fresh implementor gets its prompt with the message after it. A stored job at the old `fix` step moves to implement this way (`migrateRemovedSteps`), resuming the newest implement session the store knows.

**Enforced on the command line.** Every session gets `--disallowedTools` with `Bash(git push --force*)`, `Bash(git push -f*)` and `Bash(*--no-verify*)`, and from level 4 also `Bash(git push*)`: Scope Soup merges there. After every session Scope Soup fetches the remote's main and checks it moved only fast-forward from the commit it last saw (`src/orchestrator/mainGuard.ts`); otherwise it pauses the three agent roles with the reason.

**Agent providers.** Everything that depends on which agent CLI runs a session sits behind one interface, `AgentProvider` in `src/orchestrator/agent.ts`, with one implementation per CLI in `src/orchestrator/providers/<name>/`. Claude Code (`providers/claude/`) and GitHub Copilot CLI (`providers/copilot/`) are the two today. A provider answers the six points of `docs/research/providers.md`:
- start and events: `launch` builds the command line (prompt, model, turn limit, the role's command list) and `reader` reads its stdout as events (`init` with the session id, `action`, `usage`, `result`) and tells a limit hit apart;
- resume: `launch` with the agent's session id from `init`;
- command limits: `commandLimit` says what the CLI enforces, `"allowlist"` (it refuses every command not on `roles.<role>.allowedTools`) or `"sandbox"` (a sandbox with deny rules). The runner starts sessions only on `"allowlist"` until a person decides otherwise. `commandsText` is the `{{allowedCommands}}` text and `refusedProgram` the advice after a refusal;
- MCP servers: `roles.<role>.mcpServers` become the CLI's own inline option (`--mcp-config`, `--additional-mcp-config`); the configuration adds `mcp__<server>` to the role's `allowedTools`, and `commandsText` names the servers (`providers/mcp.ts`). Nothing is written to disk;
- usage: `usage` events in the stream, or `readUsage`, a call of its own that the runner makes once a session is over, for a CLI whose stream has no usage;
- structured answers: `launch` gets the role's schema; the `result` event carries the answer. Copilot has no schema output: its `driver.ts` runs the CLI, checks the last message against the schema and resumes the session once to ask again. `refuses` names a role a CLI cannot hold to the core rules (Copilot and any git command beyond reading, for which it cannot refuse `--no-verify`);
- reading a finished stream file for the board: a chat turn's reply, the tool calls, the tokens. Each session records its provider (`Session.provider`), so its file is read by the one that wrote it.

Which provider a session runs on is `providerFor` in `providers/index.ts`: the role's `provider`, else Claude. The test fakes are `providers/claude/fake-claude.ts` and `providers/copilot/fake-copilot.ts`, stand-ins for the CLIs; Copilot's recorded streams, made synthetic, are in `providers/copilot/fixtures/`; runner tests also pass fake providers that wrap one. A test (`providers/boundary.test.ts`) checks that nothing outside a provider's folder names its CLI, its flags or its event format, apart from a short explained list (the configuration sections, the provider list, the demo's canned streams, the queue trial).

The agent runner:
- spawns the provider's executable directly, with stream output, and has the provider parse lines defensively (keep the raw line, count malformed ones);
- records every child process id in the store, kills whole process trees on stop, and sweeps leftovers at startup;
- treats no stream event for N minutes as a stall;
- manages git worktrees itself, reused across items like a pool (`src/orchestrator/slots.ts`), or hands out full clones from a pool when the project is a submodule of an outer repository (`src/orchestrator/workspaces.ts`). Before each implement or review session and each check it runs the project's setup when it must (`setupCommand`, `src/orchestrator/setup.ts`). Before a worktree is freed when the Item is parked, its uncommitted edits are kept as a patch in the streams folder (`<streamsDir>/wip/<workspace>.diff`, `src/orchestrator/wip.ts`) and put back, with a note to the session, when the item resumes.
- fetches the remote's main before every session (`freshBase` in `src/orchestrator/runner.ts`; the guard's fetch in `src/orchestrator/worktree.ts` the same) and then moves the clone's local main branch to it (`followRemoteMain`, decision 107), so `git log main` in Scope Soup's own clone or a pool clone is not months old. A main checked out in a worktree is fast-forwarded there when its tracked files are clean (`merge --ff-only`); a dirty one, or one with commits no other branch holds, is left (never reset). Left is said once as `orchestrator.main_not_moved`. Prompts still compare with `{{base}}`, the remote's main.

**Limited resources (decision 74, `src/orchestrator/resources.ts`).** The configuration declares resources with a number of units, what needs them (roles and the check) and per-unit environment variables. The tick takes a unit of each resource the step needs (all or none) before the workspace and the claim, so an Item without one waits without writing anything to the host, and the next Item may still start; the units' variables go to the session in its environment. The runner gives a session's units back when it is over, by its Item's key, however it ended (also for a session that never started); the tick gives them back itself when the start did not happen. A chat turn takes units like a session. The queue's check takes them before each check (holder `check`) and gives them back after; without one the drain stops and the effect waits for a later drain, with no pause. This machine's units are counted in memory; a shared resource's unit is also a lease on the project's remote, `refs/scopesoup/resources/<name>/<unit>`, made with the merge queue's lease code (`mergeQueue.ts`, which takes the ref's name), held by the machine's name and lasting the longest a session or check may run, so there is no renewal. At start Scope Soup gives back everything, here and its leases on the remote. What is held, what waits and what other machines held when this one last tried is the kv value `resources`, which the board reads with the declared resources (`ResourcesView`). The Merge queue page shows them; the page of an Item that waits for a unit says so, with the resource and since when.

The usage check is a pure function over the newest usage sample (5-hour and weekly windows from `rate_limit_event`), the reset times and the reserve kept for people's own use (the `reserveFiveHour` and `reserveSevenDay` settings, one per window, always applied from level 1; `docs/RUNNING.md`). A session cut off by a limit is resumed after the reset.

**The level and the switches.** The project's `level` (0 to 4, default 0) gates the tick: nothing at 0, triages at 1, implement from 2, review from 3, merging through the merge queue at 4 (`docs/RULES.md`, `docs/RUNNING.md`, "Levels"). Each agent role (triage, implementors, review) has its own switch, and nothing of a role starts while it is paused while the others go on; nothing merges while the merge queue is paused. Scope Soup comes up with all four paused after every start-up. When nothing starts, the status line says why, naming what is paused first.

## Board

Hash routes (`web/src/route.ts`), a header with the six views and the Sync now and Stop buttons (the nav wraps whole words on a phone). The four switches (`src/store/control.ts`, `web/src/switches.ts`), each Pause or Resume, sit in the headers of the lanes they feed: triage on Backlog, implementors on In progress, review on In review, the merge queue on Merge queue; a paused lane is muted and says so, and a switch is not shown below the level that uses its role. While any switch shown at the level is paused, a bar under the header names them ("Paused: implementors, review, merge queue"; when all are paused, "Everything is paused") with one Resume all button that presses each one's own Resume, so History records it as the lane buttons do. The idle reason names "review is paused" and "the merge queue is paused" (with how many items wait) as it does implementors (decision 109):

- **Overview** (`#/`): lanes (blocked, backlog, in progress, in review, merge queue, done; the core's Queued and Checking lanes are one Merge queue lane on the overview, while cards elsewhere, the Item page and the Items list still say Queued or Checking; below level 4 the lane and the Merge queue tab are hidden while the queue is empty), the "your turn" list (each card says only what waits and how many: "2 questions", "a rewrite to accept", "a restructuring to accept", "to merge", "not ready", "escalated"; opening the Item shows the details), and a status line (runners, usage windows with a forecast of when each is used up, the last sync). A lane card has one short line: on a person's turn what waits, as in "your turn"; no text that repeats the lane (Queued and Done cards have none unless something is wrong); the Item page has the long reason. The Merge queue lane shows the batch under test (being prepared, checked or bisected) as its box, then a "Waiting · N" divider and the waiting changes in queue order; no finished batches (the Merge queue page has them); its count is the changes in it. Pause / Resume sits on a lane's title row, next to the count. When nothing starts it also shows the orchestrator's idle reason ("Nothing was started because ..."), and clears it once something starts. The backlog lane is in the orchestrator's planned pick order (no place numbers on the cards; each has small ▲ ▼ vote buttons) (`planOrder` in `src/orchestrator/candidates.ts`): priority, then bugs, smaller, older. From level 1 a divider puts the Items not triaged yet (no triage) below the rest, in the order their triages run: priority, then older. Cards whose item has open children (an umbrella) take no place in it. When its last sub-item is done it returns to "your turn" as "Close it if nothing is left: all N sub-items are done", and is not triaged again as a whole. A card's tags: whose turn it is when it is a person's (not inside "your turn", where the lane name is the tag), the decisions to look at, unsent answers, the session while it runs or is stalled, the theme's own tags, a priority other than major, "unblocks N" and the time; no tag for an agent's, the queue's or a runner's turn. The overview has no list of its own for the implementors' decisions or for who holds what: a card says "held by @mira" (the name as a mention, marked for the person viewing) and "2 decisions to look at", and the Item's page has the decisions (Accept or Overturn, one Send) and the holder (since when, quiet, claim ran out). The queue page shows which machine merges now on a project that several machines share, and the limited resources (the overview does not).
- **Items** (`#/items?...`): every item, open and closed, with search, filters (lane, priority, turn, label, holder, change, created by) and ready-made views. Stores nothing of its own (`src/core/item-list.ts`).
- **Queue** (`#/queue`): batches as boxes around their changes with one progress bar each; a bisect drawn as a tree under a failed batch.

It is built from what is already recorded: the Items' logs, shared by every machine (created, a triage rewrite accepted, questions and answers, holds, merges, sessions run elsewhere), this machine's stored sessions (role, model, outcome, time, cost), the merge queue's batches (merged, or failed with the Item that broke it), the Items' own decisions (recorded, accepted, overturned), the store's events (switches, upgrades, rewrites rejected; for an Item without a log, its questions, answers and merges) and the settings' log, one short row per save in plain words (`src/core/settingsWords.ts`) linking to Settings. Then the commits of the main branch and the item branches as lanes, paged 30 at a time, and one commit's message and files, read with git from `repoPath` (`src/orchestrator/history.ts`; nothing is fetched). A main commit links to the Item that merged it (`src/core/commitLinks.ts`: the commit its log or merged marker names, then the first `#N` in its subject that is an Item, then an item branch merged there); an item branch that points at a main commit with no commits of its own is tagged "starts here", not merged. "Show: 5 hours · 1 day · week · 30 days" sets the span. - **Settings** (`#/settings`): the level as five rows with what each needs, then parallel sessions, the usage reserve, the setup, the limited resources and the model of each role (`docs/RUNNING.md`).
- **Resources** (on the Merge queue page): each limited resource, who holds each unit and what waits for one.
- **Item** (`#/item/<key>`): the item page of decision 5, a dialog over the board, read top to bottom. The header has the title, one status line (the card's short text, `web/src/cardText.ts`; the wait for a resource unit only when that is why the Item is stuck), one tag row (lane, whose turn as on cards, priority, unblocks, labels) and a link naming the host ("Open on GitHub", "Open in Jira"; none for the meta branch). Below it: the Item (description, verification, blocked by and blocks, "Place in backlog: 2nd — why" with ▲ ▼, who holds it with Claim / Hand back), then what waits for the person (rewrite, questions, the implementor's decisions, decision needed, restructuring proposal, conflict; orange border while open), then the work (Rounds, Change with the change's diff against where it left the main branch, `GET /api/diff`, bounded in files and characters, `src/orchestrator/diff.ts`; Runs; Talk to a session), then the history (your answers, Log). The page has one primary button, for what waits for the person; Claim is primary only when nothing waits. An empty section is its heading and one line ("Change: none yet").

**Who is at the board.** People are equals and there is no login: the header has a person picker (the people Scope Soup knows from holds, log lines and answers, and a new name), remembered in the browser only (`web/src/person.ts`). Every request names the picked person in `X-ScopeSoup-Person`; the server builds that person's "Your turn" (`src/core/turns.ts`: questions are `anyone`'s, in every list until answered; a person's holds and hand-backs are `person` turns) and records the name on answers, takes and releases (`src/server/person.ts`).

The header's lamp is lit while sessions run, and a beam marks "your turn" only when something waits. When a tick leaves Scope Soup idle with "your turn" not empty, one desktop notification (count and first entries) is shown per stretch of waiting (`src/orchestrator/answerWait.ts`).

Progress is elapsed time over the mean of the last successful runs of the same kind, capped at 99 %. No history means an indeterminate bar. "Waiting for a runner" is its own state. Every blocked item says why in words.

**Writing items.** When the project's host can be written to (meta branch with `SCOPESOUP_META_WRITE=1`), the overview has a New item form (a New item button above the columns, which opens a dialog; the demo's in-memory Items host has it too) and the item page an Edit button. The foot of the item page has an Abandon button (a light red outline) and, on an abandoned item, Reopen (back to the backlog); neither shows on a done item, and Graveyard Shift words them Murder and Resurrect, with a solid red button. Both are State picks (`docs/RUNNING.md`, "The State menu"). `POST /api/items` takes `{ title, body?, verification?, labels?, blockedBy? }` and `POST /api/item/edit` takes `{ ref, ... }` with the fields to change (`state` too; the page's Edit has no State field). Lists may be given as comma-separated text, and items in `blockedBy` by their id. Each write adds a `created` or `edited` line to the item's log, then syncs before it answers, so the board shows it at once. An edit that changes nothing writes nothing. On GitHub with writes on, the Edit button changes an issue's title, description, verification and priority (the endpoint also its state, not `waiting`, which is not mapped on GitHub), written through by `editWork` (`docs/github-mapping.md`): the calls, then a re-read that must show them, then a sync; labels and blockers are refused there, and a failure leaves the store as it was and writes `orchestrator.host_write_failed`. On a read-only host both are refused and the board shows neither form. The item page shows the description as markdown (headings, bold and italic, nested lists, tables, quotes, rules, inline code, fenced code and links; `web/src/markdownParse.ts` parses the text into plain data and `web/src/Markdown.tsx` builds elements from it, so no HTML in an item reaches the page) and the log in words, oldest first.

**Images agents attach** (decision 91; `src/core/media.ts` has the rules, `src/orchestrator/media.ts` the files and git). The runner makes `.scopesoup/media/` (with a `.gitignore` of `*`) in the clone before a session and, once it is over and before anyone is told, moves the images that pass (extension and magic bytes agree: PNG, JPEG, GIF, WebP, SVG; 5 MB each, 20 per Item) into `<data>/media/<key>/`, where `<key>` is `mediaKey` of the Item's whole key (`host:kind:id` made safe plus a 64-bit FNV-1a hash of it, so two hosts' Item 7 never share). Links are never followed: the folder, `.scopesoup` and every entry are `lstat`ed, a link refused, and a read serves only a plain file whose real path is inside `<data>/media`. The clone's folder is emptied before each session. With `media.push` on they are also committed to **`refs/scopesoup/media/<key>`**: one flat tree of the Item's images, each commit's parent the one before, made with plumbing (`hash-object --no-filters`, `mktree`, `commit-tree` with Scope Soup as author, `update-ref` from the value read), pushed fast-forward to `remote` and recorded on the manifest. It is never merged and never part of the meta ref's history; a delete writes a commit without the image (the last one deletes the ref, here and on the remote), and `media.keepDaysAfterClose` deletes it with the folder. After each write the remote is compared with what it should be and updated when they differ: with sharing on, Scope Soup's ref pushed fast-forward; with sharing off, the remote's ref only shrinks to the images still here (a commit on top of the fetched remote tip without the others). A failed update is kept in the store (`media.pending`) and tried again every hour and after each session; a delete whose remote update failed answers 502 "Deleted here, but still on the remote". A blob read from the ref is refused above 5 MB (`cat-file -s` first), and at most 20 entries are listed. The board serves `GET /media/<item key>/<name>` from the data folder, then from the ref (fetched at most once a minute per Item when sharing is on), each read checked again, with the fixed content type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src data:; sandbox` and `Cross-Origin-Resource-Policy: same-origin`; `POST /api/item/media/delete` takes `{ ref, name }` from a picked person. The Markdown parser has an image node for `![alt](media/<name>)` with a plain image name only (any other image syntax stays text, so no URL is loaded); agents' plain text (round rows, questions, options, decisions) shows its images through the same node (`AgentText`); an option's picture sits under its button, not in it. An SVG is only ever an `<img>`. `inertText` turns each attached image into "(alt: image on the board)" for hosts, and every other image (Markdown inline or reference style, HTML `<img>`) into its alt text and address as words.

**Decisions on the item page.** An open `question` line in an item's log (meta branch) is shown on the item page with its options and recommendation and a box to answer in, whoever asked it and on whichever machine; the answer goes through `POST /api/answer` with `to` set to the question's `at`. An item in conflict shows `item.md` and each version put aside, with a button to keep each and a box to write the result as the whole `item.md`. `POST /api/item/resolve` takes `{ ref, text, supersedes }`, where `supersedes` names the versions the page showed, so a version that arrived since stays. On a host without a log (GitHub) the page links to the discussion on the host.

`GET /api/status` returns the board as JSON, for scripts and agents. `GET /api/health` answers `{ ok, seq, now }` from the store's last event number alone, for a service monitor.

## Answers

When the orchestrator puts an item down with a question, the item page shows the question, a grey note for its `context`, and the options as rows to pick (a label, the recommended one first and marked "(Recommended)", the description under it in smaller grey), with an "Other" row with a text box and one button to answer. `POST /api/answer` (`{ ref, answer, to?, question?, parkedAt? }`) keeps the answer in Scope Soup's own store, gives it to every later session on the item, and picks the item up again. On GitHub the store is the only place for it (a host has no place a sync would not overwrite). An answer is kept with `textHash` (a hash of the item's title, description and verification when it was given) and, when the question had options, their texts as `options`. When triage or another step later asks a question on the same item while an answer with the item's current `textHash` exists, and the new question is about the same decision (the same options, or mostly the same words, since triage rewords), the recorded answer is taken as the reply and a person is not asked again; the orchestrator writes `orchestrator.answer_reused`. Once the item's text has changed, the question is asked again. Triage may list several open decisions (`decisions`, the first also kept as `decision`); the job keeps all of them. A recorded answer is not reused for a set of several: a person is asked all of them. The job's open questions are then that list (`jobQuestions`), and the snapshot's parked state carries them as `questions`, each with the answer given so far. The item page lists every one in the parked panel ("Question n of m"), each with its context, its options as rows to pick and its own button; an answered one shows the answer. Each answer names its question by its index in the list (`question` in `POST /api/answer`), never by its text, together with `parkedAt`, the time of the parked state the page read (`parked.at`). With several open, an answer without `question` (and without `to`) is a 400 `QUESTION_MISSING`, `question` without `parkedAt` a 400 `PARKED_MISSING`, and an index past the end a 404 `QUESTION_NOT_FOUND`. An index sent once the item no longer is parked on several questions (they were all answered, or triage asked one question this time) is a 409 `NO_OPEN_QUESTIONS`, and one read from an earlier parked state (triage ran again and asked a new list) a 409 `PARKED_CHANGED`, so a stale page or command never answers a question it did not show. The page sends `parkedAt` with a single answer too, refused the same way when the item is parked elsewhere now. A `to` that names the log line park wrote for one of the several questions answers that question; a `to` naming any other question in the log is kept and closes that line, and counts for none of them. A question has one answer: a second one is a 409 `ALREADY_ANSWERED`, so the next session never sees two answers to it. The answer is kept as any other (naming its question and options) and in the job (`answered`), and the job is released only by the answer to the last open question (`answerQuestion`: one store transaction that reads and writes the jobs, so two answers sent at once cannot both see a question open, and a running tick's save keeps them). An earlier answer writes `orchestrator.question_answered` (`index`, `open`). The reply carries `open`, how many are still unanswered. An Item parked at triage starts over at triage, and that session gets all the answers together in its prompt, as every session on the item gets every answer. A single question is answered and released as before. Answers kept without a `textHash` (older ones) and rewrite decisions are never reused.
$1**the board answers an Item's questions like a dialog, sent together.** All of an Item's open questions (the Item's several questions or its one decision, an escalation's reason, and the questions in its log) are in one panel. Each option is a button with its short description, the recommended one first and marked "(Recommended)", and every question has a free-text "Other"; a question the triage marks `multiSelect` takes several options, sent as one answer joined with "; ". What is picked stays in the browser (localStorage, one entry per Item keyed by question id, `web/src/heldAnswers.ts`) until Send, so a reload keeps it. Send is one `POST /api/answers` (`{ ref, parkedAt?, answers: [{ answer, to?, question? }] }`, each entry named as in `POST /api/answer`): the answers are recorded in one store transaction or not at all (a refused one rolls back the others; two answers to one question are a 400 `DUPLICATE_ANSWER`), written in one write (GitHub: one answer comment; the meta branch: one commit with an `answer` line per question), and the item is picked up once, after them. A partial Send is allowed: the questions left out stay open. A triage rewrite keeps its own panel: its questions start at the recommendations and use the same buttons, held answers and multi-select, and Accept, Edit, Reject or "Send my answers" is one call that sends them with the decision (on GitHub one comment: the answers and, keeping every recommendation, the decision on the rewrite).

**Starting over.** An item parked as "needs-decision" or "escalated" from its implement step (`resumesStep`; not a proposed restructuring, not a retry of the hand-over) shows a **Start over** button (`canStartOver` on the item page and in the snapshot's parked state). `POST /api/start-over` (`{ ref }`) drops the job (branch, review round and findings with it) through `releaseJob` with `startOver`, so the item starts at triage. It is a 200 `{ started: true }`, a 404 `ITEM_NOT_FOUND`, and a 409 `NOT_PARKED` when the item is not parked that way. An ordinary answer does not start over; see below.

**Talking to a session.** The Item page has a panel listing the Item's sessions Scope Soup knows (each stored session's `agentSessionId`, whatever its role), newest first; a person picks one and writes. Each message is one more turn of that session (`src/orchestrator/chat.ts`): the runner starts `claude -p --resume <session>` in the Item's worktree with only the message, the role's model, permission mode and allowed tools (a triage or a reviewer stays read-only) and `--include-partial-messages`, but without the role's answer schema. The turn is a session with `chat: true`; it never becomes the job's `sessionId`, so its free-text reply is never read as the role's answer and the Item stays where it was (parked state, step and findings unchanged; only `agentSession` follows a forked session id). `POST /api/chat` (`{ ref, session, message }`) answers 202 once the turn has started; `GET /api/chat?ref=` gives the sessions with their turns and `blocked`, the reason no message can be sent now. The page polls it each second while a turn runs, so the reply shows as it is written (read from the turn's stream file), and refetches on events otherwise. A message is refused (409 `CHAT_REFUSED`) while any session runs on the Item (`runner.busy`, which is true from the moment a start is asked for), while a turn is still answered, after Stop, while a person holds the Item, at the usage stop (the tick's usage check), while the Item is queued for merging, being merged or owes its hand-over (level 4: the branch is the queue's), once it is merged, and when the Item has no job (no work under way, so no worktree). On a done or abandoned Item the page shows the past turns and no box to write in. `claude` keeps a session per folder, so every session records the folder it ran in (`cwd`) and a turn runs only there: in a pool of clones it is refused, with the reason, when that folder is gone, is not a clone of the pool any more, now holds another Item's work, is not the clone the Item's work is in, or was not recorded (a session from before), and a clone the pool hands out that is not the session's goes back at once. While a turn runs the tick starts nothing on the Item and counts the turn as a running session. A worktree or clone the turn had to make for a parked Item is freed again after it. The conversation is kept in the store (`chat:<item>`), not on the host; events `orchestrator.chat_sent`, `orchestrator.chat_answered` and `orchestrator.chat_failed`.

## Agents push back

An answer to a question or an escalation from implement (`POST /api/answer`) resumes that step: the job keeps its step, review round and findings, and the next session is the same step with the answer in its prompt (or, when the implementor's session is resumed, after its message). An answer to a triage question starts at triage, and so does an answer to a round-limit escalation (from review: the limit is spent, so the item starts over with the answer passed on), and an answer to an Item parked at merging or a closed change, which drops the job. An answer to an Item parked at hand-over keeps the job and only repeats the hand-over.

An agent can stop for a person in two ways besides a question from triage (triage itself may ask several at once, see "Answers").

**A question with options from the implementer.** The answer of implement may carry `question` (`question`, `options`, `recommendation`), exactly as triage's. The item is parked as "needs-decision", the item page shows the question with the options as one-tap choices, and the `question` line in the log carries them. Like triage's, it always goes to a person, whatever the risk and whether a recommendation is given; Scope Soup never takes the recommendation itself. A question a person already answered on the unchanged item is answered from the record and the same step runs again, at most three times per item. An answer that is not done and has no `question` parks the item with its `summary` as the reason; one that stopped after a refused command is parked as escalated, with the advice on `allowedTools`.

**The triage rewrites the description.** The triage searches and reads the other Items with the item commands: the triage role's default `allowedTools` add `Bash(pnpm --dir {{scopesoup}} item list*)` and `Bash(pnpm --dir {{scopesoup}} item show*)`, where `{{scopesoup}}` is the folder Scope Soup runs from (filled in when the configuration is read; a role's own list may use it too), and sessions get `SCOPESOUP_CONFIG` so the commands find the project. Its answer adds `rewrite` (the description written as if a person takes every recommendation) and `links` (`blockedBy`, `blocks`, `duplicateOf`, `conflictsWith`, `related`, each with the other Item's id and why).
- A `blockedBy` link to an open Item is the only one acted on by itself: on the meta branch Scope Soup records it as its own blocker (in its store, `orchestrator.blockers_recorded`, and in the item's `blockedBy` field, with an `edited` line). On GitHub the blockers are the issue's dependencies (decision 49, which reverses an earlier decision): Scope Soup writes `blocked_by` on the issue, and the re-read, not its store, makes the Item blocked; a write that fails writes `orchestrator.host_write_failed` and parks the Item as escalated. A `blocks` link is written there as `blocked_by` on the other open issue. Then it closes the job (`orchestrator.blocked`), and the Item waits in Blocked. Once the blocker is done the triage runs again; on the meta branch a later triage without the blocker drops Scope Soup's record, while on GitHub nothing is removed (a person may have added the dependency).
- A `duplicateOf` link (this Item repeats the named one) becomes a question with triage's reason in it ("Triage found A-3 a duplicate of A-1 "…". Its reason: … Which one closes?"): "Close A-3 as a duplicate of A-1" (recommended), "Close A-1 as a duplicate of A-3", or "Keep both" (decision 113). Once the rewrite is settled, closing A-3 closes it on the host where Scope Soup can (GitHub, Jira, the meta branch with writes on), else parks it as not ready; closing A-1 closes that one the same way and A-3 goes on, unless that could lose work (a session, a chat, someone else's hold, a job not parked, a change in review, queued, merged or handed over, `doing` with no job, or commits on its branch ahead of main): then A-1 stays open and the event says so. Every "close the other" answer of a round is done; with "close this Item" too, the others stay open and an event says so. A `conflictsWith` link becomes "A-3 conflicts with A-1 … Go on with both, or hold A-3 until A-1 is done?", with "Go on with both" recommended: touching the same files is normal, and whichever lands second merges. Picking the hold keeps the rewrite too (it does not change the description) and, once settled, makes the Item blocked by the other one as a `blockedBy` link does (below); it waits in Blocked and its triage runs again once that one is done. The answer is kept per pair (`pairAnswer`, the newest answer to that question asked on either Item, read from the recorded answers: on GitHub the answer comments, elsewhere Scope Soup's store; never reused by text hash like other answers). After a "go on" no later triage of either Item asks about the pair again. A hold stays a blocker in every later triage of the held Item while the other is open, whatever that triage's links say, so a hold answered together with another answer (which runs the triage again), or whose GitHub write failed, still blocks. No hold is offered, or written, when the other Item already waits on this one (its `blockedBy`, Scope Soup's blockers or a hold, directly or through other Items): a hold that would close the cycle parks the Item as escalated and nothing is held. Nothing is asked about an Item that is closed or Done (its change merged), and a hold for an Item done meanwhile lets the work go on. A `conflictsWith` link (from either Item's triage) also makes the Item's first implement step wait while the other is busy, as for overlapping paths (`sameFilesWait`, `src/orchestrator/candidates.ts`; busy lasts until the change is on main), unless a person answered "Go on with both" for the pair (decision 115). `related` (and `blocks`) are shown on the Item page and to the implementor (`{{linked}}`).
- With questions, or a rewrite that differs from the description, the item is parked (a rewrite that differs only in whitespace, or only by a Verification part repeating the Item's verification field, which is cut from any rewrite, does not differ: decision 110) as "needs-decision" on the rewrite (the job's `rewrite`; one `question` line in the log with `rewrite` naming the round). The Item page shows each question with its recommendation picked to begin with, next to the description before and the rewrite after. Keeping every recommendation, one press accepts the rewrite (also Edit and Reject); picking any other answer (other than a link question's stopping answer: close as a duplicate, hold for a conflict) shows one "Send my answers" button instead, and the triage runs again with the answers in its prompt and writes a new rewrite, round after round with no cap. `POST /api/rewrite` (`{ ref, parkedAt, answers, action, text? }`, one answer per question in order) records the answers as a person's (given to every later session). Accept or Edit writes the text as the item's description (an `edited` line with `via: "triage, round n"` and `was`, the text it replaced, which the history shows; on GitHub with writes on only the description part of the issue's body is replaced with the text, made inert, and its `## Verification` section is kept (`editWork`); when that fails or writes are off the text is recorded as an answer the agents use in place of the host's, naming the failure, with an `orchestrator.host_write_failed` event); Reject keeps the description and sends nothing. Events: `orchestrator.rewrite_accepted`, `_edited`, `_rejected`, or `orchestrator.rewrite_answered` for a new round. Refusals: 400 `ANSWERS_MISSING`, 409 `NO_REWRITE`, 409 `PARKED_CHANGED`. Once settled, the next tick goes on from triage's other verdicts (a restructuring, not ready, or implement), so from level 2 no implementor starts before a person accepted or rejected the final rewrite. An item that states its size skips the triage as before.
- The rewrite may carry label changes (`rewrite.labels`, kept to the host's existing labels and never `scopesoup:*`; a label the host does not have is dropped and noted in `rewrite.droppedLabels` and the reason the Item is parked). The Item page shows them as `+bug, −question`; Accept applies them with the description, Edit (`labels` in `POST /api/rewrite`) changes both, Reject applies neither. At Accept only the changes that still make sense are applied: on GitHub one call per label and a re-read (`docs/github-mapping.md`, "Labels in a rewrite"), on the meta branch in the same edit as the description.
- **Item drafts** (decision 95). Triage, the implementor and the reviewer may list `drafts` (title, description, verification) in their answer; a review's `should` findings may become one. `src/orchestrator/drafts.ts` files each as an `ItemDraft` object in the store (host `scopesoup`, kind `draft`, id from the source Item and the normalized title and description, so it is filed once; `draft.created`), its text made inert (`inertDraft`: `inertText`, no hidden marks, marker-shaped lines and any "(draft <id>)" broken). The board lists the open ones in Your turn (`BoardView.drafts`, `src/server/drafts.ts`); `POST /api/item-draft` approves (the source Item's host's `createWork`, from the `restructure` hosts; the text ends `Found while working on #N (draft <id>).`; Approve first records `approving` on the draft, and an Approve that did not finish is retried after a sync, taking the Item whose last line is exactly that marker and that no other draft's decision took) or denies. The decision stays on the object (`draft.updated`, shown in History). Nothing is written to a host or the meta ref before Approve.
- **Questions about other Items.** Triage and the implementor may add `aboutOthers` to their answer: for another Item (its id), questions with options and a recommendation, and from triage only a `rewrite` of that Item's description. Scope Soup writes them there, not the agent: each question ends "(asked by triage of A-3)" or "(asked by the implementor of A-12)", and the Item parks on them as on triage's own rewrite (`rewrite` with `askedBy`; the rewrite is the description as it is when none was given), with the same Accept, Edit and Reject and the same handling on the host (comments made inert on GitHub, one `question` line on the meta branch). Allowed on any open Item, also one with paused work (a parked job keeps its branch, its implementor's session and findings), when no session or chat turn runs on it, nobody else holds it, and it waits for no answer of its own, no review and no merge or hand-over (a change in review is not pulled back to triage); until then they wait in the store (`orchestrator.aboutOthers`, by the Item's ref key; `orchestrator.about_other_kept`, `_wait`, `_written`). An unknown or closed Item drops them (`orchestrator.about_other_dropped`), and so is a question asked there before (#43): the same question, matched as answers are for reuse (the asker named in its text), that already waits for the Item, is open on it, or was answered on it while its text is as it is now (`askedBefore`). Once answered, the Item is triaged again with the answers. No cap. A rewrite from triage with no question (none given, or each one asked before) is not written that way (decision 110): it never touches the Item's job. It is kept as a proposed rewrite of that Item (`orchestrator.proposedRewrites`, by ref key, a newer one replacing it; `orchestrator.rewrite_proposed`), on this machine's board only, never posted on the host. The snapshot's `proposedRewrites` (open Items whose description does not read as the rewrite already) give the Item page `proposedRewrite` (a panel with the change, Accept, Edit and Reject) and, in the backlog or Blocked with no session running, a "your turn" card "a rewrite to accept". `POST /api/proposed-rewrite` (`{ ref, at, action, text? }`) writes Accept or Edit as an accepted triage rewrite is written (the `edited` line with `via: "rewrite by triage of A-3"`, GitHub's body, else an answer the agents use; the AI label as for a triage rewrite), counted as the text the Item's triage saw (`adoptWritten`), and Reject drops it; the job carries on as it is, and nothing starts a triage. Refusals: 409 `NO_REWRITE` (none, or another one now), 409 `BODY_CHANGED` (Accept after the description was edited), 400 `WRITE_REFUSED`. A rewrite that is the description, whitespace aside, is dropped when it is kept and again, with questions, when it is written.
- A rewrite that keeps the description (whitespace aside), asks nothing and proposes no label change goes on at once. An answer without `rewrite` (a session started before the upgrade) is settled as before; jobs already past triage are not gated; old question lines and jobs stay readable, and a parked rewrite rebuilt from the log after `data/` is lost comes back as a plain question whose answer starts the triage again.

**Triage again.** A job waiting at its implement step with nothing of the step begun (`awaitsImplement` in `src/orchestrator/recheck.ts`) is checked when the tick is about to start that step: its triage is out of date when commits on main touch the paths it named since (the runner's `commitsTouching`, `git log since..main -- <paths>`, from the main `watchMain` read right after the triage), the Item's text hash differs from the one the triage was given (`job.triaging`, kept as `job.triaged` with the answer; hashes of descriptions Scope Soup wrote from an accepted rewrite count as the same text), a blocker open then is done, or it is older than `settings.triageMaxAgeDays`. Then the job goes back to `triage` with `recheck` (the reasons, the previous answer, the commits, the old text), rendered into `{{recheck}}`; the answer clears it. See docs/RUNNING.md, "A triage again".

**No proposed rewrites from other steps.** A session that finds the item's description or verification wrong asks a question with options (the separate rewrite flow with a diff is gone; the rewrite loop came back in the triage only). A job stored parked on a proposed rewrite is released by the tick after the upgrade (an `orchestrator.job_released` event), so the item starts over at triage; an open rewrite question line in an item's log no longer holds the item.

**The fence and progress.** The triage's `paths` and `size` are read again after the build: from level 3, before review, the program compares the branch's change (`changeStat` on the runner: each changed path with its added plus removed lines) with them (`src/core/fence.ts`, pure). A change well beyond them parks the implement step as a decision (`orchestrator.fenced`, `job.decision`) with the report and a proposed split in words; the answer resumes the implementor (`resumeWith` holds the report), and `job.fence` keeps what the person saw, which widens the fence. The review step keeps `job.progress` (the last round's `must` count and finding keys, and the last merging failure's key, `failureKey` in `queueMerge.ts`) and escalates a round that gets nowhere (`noProgress` in `src/orchestrator/progress.ts`). An approval's `should` findings go back to the implementor once (`job.shouldSent`, `job.shouldRound`; not counted in `fixRounds`; a round that commits nothing goes on to the merge) or become one Item draft (`review.shouldFindings`). `docs/AUTONOMY.md` gives the limits.

**A proposed restructuring** (decision 94). Triage may give `restructure`: a `reason`, what becomes of the item (`original`: it `keeps` one part, becomes an `umbrella`, or is `replaced`), and `parts`, each a `title`, a `description`, a `verification` and where it `goes`: `original` (the part the item keeps), a new `child` under it, a new `related` Item, a new `unlinked` Item, or `into` an existing Item named by `into`. The item keeps a part exactly when one part goes `original` and another goes elsewhere; an umbrella has a child; a duplicate is `replaced` with one part `into` the Item it duplicates. A restructuring that does not hold together is left out of the answer. With one the item is parked as "needs-decision" (the job's `proposal`, and the `question` line's `proposal` with its `id`, `original`, `parts` and `carried`; the `id` is a hash of the Item and the time, so each restructuring of an Item has its own), whatever `ready` or `size` says; a large item without one is parked as "not-ready", too large, as before. A part `into` an Item the store knows is named by that Item's id. The decisions already made on the item are carried over into each new part (`carried`): a person's recorded answers (not their verdicts on earlier proposals). The item page lists the parts with where each goes (a part into an existing Item with that Item's title, its state, and a note when it has an open change or an agent on it) and the item's fate, with Accept, Edit (a person changes the parts' text, where each goes, adds or removes parts, and changes the fate; an Item typed in is looked up as it is typed) and Reject, through `POST /api/proposal` (`{ ref, action, parts?, original?, to? }`). Nothing is made before Accept:

- Accept, or Edit with a person's version, makes the parts through the item's own host, in order, with text made inert: a child with `createWork` and `parent` (a sub-issue on GitHub, a sub-task on Jira, a child Item on the meta branch), a related Item, then linked with `linkRelated` where the host keeps such links (Jira: "relates to", added only when missing, so a retry or an adopted part gets it once; on GitHub the marker line's `#N` links it), an unlinked Item with neither, and the parts `into` an Item as `## Added from <item>: <title>` sections at the end of that Item's description: all of one Item's parts in one `editWork`, to the description as read from the host just before (`RestructureHost.read`), skipping a section whose marker is there already; a re-read must show every marker, else the accept stops (a person's edit at the same moment loses nothing silently), and a `BodyChanged` from the host stops it too. New parts carry the decisions as a section of their text (GitHub, which has no verification field, gets the verification as a `## Verification` section too). Each part's text ends with a marker line, `Part <n> of restructuring <id> of <item>.`, naming the item `#N` on GitHub and by its ref key elsewhere and for an unlinked part (so GitHub makes no link). Agent text is made inert and any line in it shaped like a marker is broken (`inertPart`), so it cannot pose as a part. Then the item itself: one that keeps a part gets that part's title, description and verification (`editWork`) and is released, so triage looks at it again; an umbrella is parked as "not-ready" with the parts named; a replaced item is closed as abandoned (refused, 409 `ITEM_BUSY`, before anything is made while it has an open change, an agent session or a running job) (`editWork`, as a duplicate of the one Item when it is replaced by a single part into an existing Item), and the decision names what replaced it.
- What was made is recorded in the job as it is made (`orchestrator.restructure_part_made`), each part with its index and whether it is linked. On GitHub the sub-issue link is a call of its own: when it fails, `createWork` still returns the issue (`linked: false`), the child is recorded unlinked, and the accept stops with the reason. Before it makes anything, an accept also looks on the host (the synced items) for items carrying the marker lines (a new part under its title, a part `into` an Item only in that Item), and records those it did not know (`orchestrator.restructure_parts_found`), so a store rebuilt after `data/` was deleted, or a part made by hand from the text, is not made again. It then links each recorded child that is not linked (`linkChild`) and makes only the missing parts. A part `into` an Item that is not another Item on the host (400 `BAD_TARGET`), or one that is done or abandoned (400 `TARGET_CLOSED`), is refused before anything is made. A second press while the parts are being made is refused. Once a part exists the restructuring is fixed: an edit is refused (409 `PARTS_CREATED`), and the page offers Accept (finish it) and **Stop here** (`action: "stop"`): it ends the restructuring with the parts made so far, leaves the Item as it is, and records the rest (the parts not made and the Item's fate) as text on the Item for a person, parking it as "not-ready" (`orchestrator.restructure_stopped`). The item's own change goes last, so a retry after it failed finds every part and only does it again. When all is done the decision is recorded as an answer (`orchestrator.restructure_done`).
- On a host Scope Soup cannot create items on (`write: false`, a GitHub clone whose remote is another repository, or a host not configured for writing), accepting makes nothing: the decision is recorded with the restructuring as text (marker lines included), for a person to carry out by hand, and the item is parked as "not-ready" saying so. With both a GitHub and a meta branch host configured, each item's restructuring goes to its own host.
- Reject records the rejection as an answer and starts the item over at triage, which is given it ("do not propose it again"). Once any part exists, Reject is refused (409) and not offered: it would leave the parts without the decision.
A restructuring is always a person's to decide.

## The orchestrator's progress in the item's log

On a host that keeps a log per item (meta branch), the local store is never the only copy of where an item stands. The orchestrator writes:

- `claimed` and `released` for its own sessions, when the meta branch has writes on and a remote to share it with. A person's claim is written by `pnpm item claim` (`until` is ten years ahead, and the board does not show it; `from` says where it came from) and the hand-back by a `revision` line with `handback: true` and a `released` line (`docs/RUNNING.md`, "Item commands").
- `session` when a session ends, with `next`, the step the item goes to now. No transcript.
- `question` when it puts the item down for a person, with `parked` (why it is parked) and, for a decision from triage or the implementer, the options and the recommendation; for a proposed restructuring, `proposal`. When triage lists several decisions, each is written as its own `question` line (with its options, recommendation and context), and a person entry on the board names how many questions wait. An answer from the board to one of them names that line (`to`), found by its question text, so each closes on its own.
- Not a log line: when a question reuses a person's recorded answer on an unchanged item (see "Answers"), the store gets an `orchestrator.answer_reused` event and a person is not asked.
- `revision` when the branch has a new head after implement, and `review` with the verdict and the findings on that head.
- `check`, `revision` and `merged` at merging (level 4), and `revision` and `merged` when the implementing session merged (levels 2 and 3). Now the `check` line is written: `pass` on the merged commit with its batch when the queue merges it (not when the main branch was moved by someone else), and `fail` on the change's commit with the failing check's name or the check command's last lines in `findings` (cut to 2,000 characters) when a red batch sends it back. A conflict in the batch is not a check and has no line.

**The Rounds table.** The Item page shows the cycle as a table built from these lines alone (`src/core/rounds.ts`): one row per step (triage, implement, review, implement resumed with the findings, ..., the check at level 4) with its model, what it found or decided (the triage's verdict and questions, each review finding with its severity, the check's result), what it did (the implementor's summary and commits), how long it took and what it cost, and a last row for the outcome (merged, escalated and why, waiting for you; from the orchestrator's parked state, else from the newest unanswered question line with `parked`). A step's own lines come before its `session` line, so they are gathered until it. The cost and the links come from the line's `sessionId` and `costUsd`; for an older line without them, from the store's session of that role that ended closest before the line. On GitHub the same lines come from the log comment. Each row with a session opens its details one click away: `GET /api/session?id=` gives the session record, the tools it called and each call in a few words, read from its stream file (`src/server/sessionDetails.ts`), and a button that picks that session in the chat panel.

`POST /api/answer` writes `answer`, naming the question by `to` (its `at`) and `toBy` (its `by`): the question named by `to` in the request, else the newest open one. The decision on a proposed restructuring writes `answer` the same way, with `proposal` set to `accepted`, `edited` or `rejected`.

**Read back.** The first tick that sees an item in the store (`orchestrator.logs_read` lists them) rebuilds its job and its answers from its log, when the store has none (`src/orchestrator/recover.ts`). So deleting `data/` loses nothing that matters:

1. An open question by Scope Soup (a proposed restructuring too): the item is parked, waiting for the answer. When triage asked several questions, the Item's newest open question lines (`parked: needs-decision`, written one after the other) all come back, in log order, as triage's `decisions`, so the item waits for every one of them again; the parked `at` is that of the first of those lines, and the page sends it back as `parkedAt`.
2. The last `session` names a `next` step: that step starts again.
3. The newest revision has a passing review and has not merged: the hand-over (merging) is done again, without a session.
4. Anything else: the item starts as a new item. The answers from the log go to its sessions.

The step and the review round live in the job, not in the log. So after `data/` is deleted, an answered question or escalation from implement has no job to resume, and the item restarts at triage (case 4) with the answer in its prompt.

An item's change on such a host has the item's own id. It is Scope Soup's own work on the item's branch, so it does not hold the item back when the item starts over.

Only for one laptop: lines are read back by `who` (`scopesoup`), not by machine. With a pool of clones the clone that held the branch is not known after the store is deleted. A hand-over rebuilt this way, or one a person retries after the Item was parked, holds no clone, so it takes a clone again on the item's branch (and waits, saying so on the item, while none is free) and then goes on; the item is not started over. On GitHub the same record is kept on the issue instead: the log comment, the question and answer comments, and the claim comment (`docs/github-mapping.md`).

## Design rules

Rules every change to Scope Soup keeps. A reviewer reads them here, with the rest of the project's docs; Scope Soup no longer puts them in the review prompt. Keep each rule one line; add one when a review misses something a person then catches.

- Never await long work in the tick. A check, a session or a host call that can take minutes runs beside the tick and is picked up on a later one; dispatch must not stall.
- Server actions on jobs go through one store transaction, and every state change writes its event in that same transaction.
- A fake refuses what the real port refuses. A test double of the queue, a host or the store must reject the same inputs the real one rejects, or a test on it proves nothing.
- A change of what Scope Soup writes to a host is a person's to decide before it is merged.
