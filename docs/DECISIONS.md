# Decisions

Issue numbers written GF-n refer to the tracker of the earlier private repository and are not issues here.

Decisions the owner has made, newest last. Open questions are at the end. Do not assume answers to open questions; ask.

Note (GF-403, decision 69): Scope Soup has no owner. The people on a project are equals and trust each other; anyone answers Scope Soup's questions and releases anyone's hold. Where an older decision below speaks of "the owner" as a role in Scope Soup (who answers, approves, releases or is notified), read "the people on the project". Where it says who made a decision, it is history and stays as written.

Background: Scope Soup grew out of the owner's earlier agent setup (a backlog tool, a merge queue, orchestrator rules). The research that led here is in `docs/research/`.

## Made on 2026-11-22: a format number for the config file (GF-145)

| # | Decision | Choice |
|---|---|---|
| 62 | The config file's format | `version` in `scopesoup.config.json` is a format number: a whole number raised only when an older file would no longer load as it is. A file without it is format 0 (release 0.5.0 and everything before); GF-145 makes the current format 1, and everything Scope Soup writes (the Settings page, onboarding, the example, this repository's own file) carries `"version": 1`. At start an older file is migrated: one step in code per format (`src/config/migrate.ts`), the file rewritten in the current format, one copy of the old file kept beside it as `scopesoup.config.v<old>.json` (only the newest copy is kept), and a one-time notice says what changed. The keys that used to load with an "ignored" notice are dropped or converted by the step from 0 to 1 (`dryRun` and a string `landing` become `level`; `settings.parallelSessions` is merged into `maxParallelSessions`); in a format-1 file they are unknown keys. A file newer than this Scope Soup is refused with "this project's config is from a newer Scope Soup; upgrade Scope Soup" and left untouched. A file that would not load after migrating (say, no `machineName`, which no step can invent) is not written: start fails with the usual message, and the file is migrated once it loads. A file that cannot be written fails the start with a clear message and is not changed. The item commands read an older file migrated in memory and leave it alone; `pnpm config:check` only reports. Release notes say when the format changes. |

## Made on 2026-11-22: a format number for the meta branch (GF-359)

| # | Decision | Choice |
|---|---|---|
| 63 | The meta branch's format | A file `format` at the root of the meta tree holds the format: a whole number and a line end, raised only for a breaking change (a field whose meaning changes, a new required field, a moved file). New log kinds and optional fields need no new format. A meta branch without the file is format 0 (everything written before GF-359); GF-359 makes the current format 1, which is format 0 with the file, so the step from 0 to 1 only writes it. ## Made on 2026-11-22: a schema version for the database (GF-360)

| # | Decision | Choice |
|---|---|---|
| 64 | The database's schema version | `PRAGMA user_version` in `scopesoup.sqlite` is the schema version: a whole number raised only when the schema changes. A database without one is version 0 (everything before GF-360); GF-360 makes the current version 1, which is version 0 with the number set, and a new database starts at it. Steps are code, one per version (`src/store/schema.ts`). Every open goes through `openStore` (`src/store/store.ts`), the server's and the tests'; nothing else opens the file. An older database is migrated at open in one transaction (`BEGIN IMMEDIATE`, the version read again inside it, so two processes do not both migrate), keeping every row; a failed step leaves it unchanged. Before a step marked as changing what an older Scope Soup reads, one copy is kept beside the database as `scopesoup.v<old>.sqlite` (`VACUUM INTO`; only the newest copy is kept), so going back across a breaking change is the old folder plus that copy (the owner's upgrade policy, GF-145). The step from 0 to 1 keeps no copy: it only sets the number (and makes a missing table, as older opens did), and an older Scope Soup reads version 1 as it is. The server prints the migration once and writes `scopesoup.store_migrated`. A database newer than this Scope Soup is opened read only without touching the disk (immutable when no `-wal` is beside it, so no `-wal` or `-shm` is made): reads work and every write (put, remove, appendEvent, setValue, addUsageSample) is refused with "this project's data is from a newer Scope Soup; upgrade". The server does not start on one, as it writes from its first tick: the start stops with that message. No downgrade migrations. Release notes say when the schema version changes. |

## Made on 2026-11-22: importing from GitHub Issues (GF-160, GF-361)

| # | Decision | Choice |
|---|---|---|
| 67 | Importing from GitHub Issues | A project whose backlog is on GitHub Issues can import it once into Items on its meta branch, and use Items from then on (`pnpm item import github --repo owner/name`). Every open issue becomes an Item (title, body, labels, priority from `priority:*`, parent and sub-issues, blocked-by links, the assignee as holder where the person is known), links between imported issues are rewritten to the new Item ids, and each Item records where it came from in an optional header field `importedFrom: github:owner/name#N` (older ScopeSoups keep and ignore it, decision 63) and a link in its body, so a second run imports nothing twice. Closed issues are left out unless asked for (the last N, or all); pull requests are never imported.
